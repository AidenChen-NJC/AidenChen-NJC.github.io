Dilution is a silent failure: no error, no flag. A rule you agreed on at turn 1 is gone by turn 100.
The popular fixes don't work: a memory vault, one agent managing another. You can't out-prompt physics.
The fix: stop asking the model to remember. Move what matters out of the window, where it can't dilute.
Then audit it. “The mechanism exists” and “the mechanism is still firing” are different facts.

1. What it is

You set a rule at the start of a session. “Update the changelog after every change.” Twenty turns in, it's still holding. Around turn one hundred it quietly stops, buried under everything that came after, and you don't notice until you go looking.

That's context dilution. It follows from three facts about LLM agents you can't engineer away. The context window fills up, so a line-one instruction fights hundreds of messages for attention by turn one hundred. There's no cross-session memory, so today's lesson is gone tomorrow. It's stochastic, so you can't bet on “it should remember.”

Together: you can't rely on an agent retaining any given rule, over a long enough session.

2. Why it's worse than a bug

A bug throws an error. A stack trace points at a line. You can fix what you can see.

Dilution shows you nothing. A rule you thought was running just stopped, at some moment you weren't watching. No error, no failing test, no red. The mechanism was there the whole time and stopped working.

And it generalizes. Every mechanism you build has three checkpoints, each able to fail silently:

  1. Designed to run: the rule exists, the logic is correct.
  2. Actually runs: wired up, registered, triggered on the right event.
  3. Actually produces a result: running, and the output is real.

Break one and the mechanism looks like it's protecting you while protecting nothing. Most people only check the first: “I wrote the rule, it's in the file.” The failures live in 2 and 3. The question is never “did I add the rule?” but “is it still firing, and is its output real?”

The internet bolts something flashy on top: Obsidian to “manage memory,” one agent supervising another so it looks organized.

A memory vault doesn't escape dilution, it reorganizes it. The notes still have to be read back into the window to do anything, where they fight for attention like everything else. Prettier storage, same physics.

The subtler version: make it remember harder. Longer configs, angrier reminders, more prompt. Same problem, because a bigger rule is still a rule competing against everything downstream.

The test isn't where the text is stored, it's whether the mechanism needs the model to notice it to work. If it does, it can be diluted. The only things that can't are the ones that act outside the model's attention entirely.

3. The fix: move it out

Two roads. Make it remember better, which is doomed. Or admit it can't, and move what matters out: to a script that fires on every action, a file system with permissions drawn, a log that compiles itself into rules. Somewhere the window can't reach.

That's the core move. The rest is the same instinct at different scopes.

One fork. Move things out as primitives (a file system, a gate, a log) or as scaffolding (instructions written to patch what today's model can't do). The smarter the model gets, the more primitives pay off and the more scaffolding you have to tear out. Build with primitives and you don't have to redo this layer when the model improves.

4. Where the rules live

They need somewhere to live, and not one file. Sort by one question: would this rule survive a long conversation? If not, it sinks.

LayerWhat lives hereDecays?
Global configSoft preferences: style, toneYes, doesn't matter
Project configProject map: what to read, who owns whatYes
Skills (load-on-match)Topic rules, loaded only when hitDoesn't bloat context
Output styleReplaces the system prompt, re-injected mid-sessionResisted, not immune
HooksHard rules, fire on every actionNo
Auto-memoryCross-session learningPersistent

If decay does no harm, it lives up top; if decay would hurt, it sinks. Hooks are bedrock: they don't live in the conversation, so no conversation is long enough to dilute them. The discipline: deterministic goes to a hook, discretionary goes to a skill. Anything that must happen belongs in a hook, never in a skill's best-effort matching.

5. How I fight it

Each defense maps to one way dilution fails you.

Hard rules sink into hooks. A pre-write gate (pretool_approval_gate.py) splits the file system into a free-write zone (drafts, notes, logs) and a canonical zone (README, the live site, anything user-facing). Reach for canonical, or try to write past a line threshold, and it stops until a recent message of mine carries an approval token. It can't be diluted, because it's not a rule in the prompt but a gate outside it, and it fires even under “skip all permission checks.” The judgment “what's it allowed to do right now” is itself state that goes missing in a long session, so I moved that out too.

Behavior rules become a re-injected layer. The output style replaces the system prompt instead of appending, and re-injects as the conversation grows, so the rules stay near the front instead of aging into the backlog. This still lives in context, so it isn't immune, only the most resistant thing that does. Replacement and recency are what separate it from “remember harder”: it refreshes the rules in place rather than piling more text on top of them.

Corrections turn into a log. When I correct it, a stop hook (stop_enforce_lessons.sh) won't end the turn until the correction lands: what went wrong, the rule, the root cause. Each lesson carries a tag. [active] means I'm still enforcing it by hand; once I move it into a hook I flip it to [codified] and it stops loading. The point of the log isn't to store corrections, it's to convert them: every lesson is meant to become a mechanism, and once it does it no longer loads into context, so the log gets cheaper to carry the more you use it.

Context survives compaction. Before the conversation gets summarized away, a hook (precompact_dump_plan.sh) dumps the plan to disk and re-reads it after, not from memory.

None of these are about the model. All of them are about the structure around it.

6. Audit it, or it does nothing

A mechanism you don't audit is indistinguishable from no mechanism. Two cases from my own system.

I wrote a hook to enforce self-critique (interrogate_enforce.py) and never registered it. For a week it fired zero times, dead code I'd checked off as done. Checkpoint 2 failed silently.

Same week, the correction-log hook above scanned the transcript for “correction signals,” but tool output was stored as the same type as my typed messages, so it matched files it had read into itself and accused me of corrections I never made. Running, producing garbage. Checkpoint 3 failed silently.

Verify a mechanism is wired and live, not that it exists. “I added the rule” is the answer that gets you hurt.

7. Build your own

Inside-out, each step paying off immediately:

  1. Learning loop first. A correction log plus a hook that won't end a turn until the correction is written. Get corrections to settle.
  2. Then the gate. Split free-write from canonical; cheap and reversible runs full speed, irreversible stops for you. This is what lets you take your hands off.
  3. Then memory. Sort rules by decay, sink the ones that must not die into hooks.
  4. Audit. Verify each mechanism fires, not that it exists.
  5. Stay lean. Ask if a layer was added for today's model and will be dead weight next version. If so, tear it out.

The signal under the noise: the model is rented, the structure around it is yours. Stop tuning the layer being commoditized. Build the one that isn't.

然後 audit 它。「機制存在」和「機制還在跑」是兩件不同的事。

一、它是什麼

你在 session 開頭訂了一條規則：「每次改完更新 changelog」。前二十輪都還在。到第一百輪它悄悄停了，被後面所有東西埋掉，而你要等到回頭去找才發現。

這就是 context dilution，來自三個你改不掉的事實。context window 會被填滿，所以第一行的指令到第一百輪，得跟幾百則訊息搶注意力。它沒有跨 session 記憶，所以今天教會的明天歸零。它是 stochastic 的，所以你不能賭「它應該記得」。

在夠長的 session 裡，你不能指望 agent 記住任何一條特定規則。

二、為什麼它比 bug 更糟

bug 會 throw、會報錯，stack trace 指到某一行。看得到的東西，你修得掉。

Dilution 不會跟你說它正在發生，但它正在發生。一條你以為還在跑的規則，在某個你沒注意的時刻就停了。沒有報錯、沒有失敗的 test、沒有紅燈。機制一直都在，只是變成了死的。

而且它會 generalize。你建的每個機制都有三道會 silent 失效的關卡：

  1. 設計上能跑：規則存在、邏輯正確。
  2. 實際有在跑：接上線、有註冊、在對的事件被觸發。
  3. 真的產生結果：在跑，而且 output 是真的。

斷任何一道，這機制就「看起來」在保護你，其實什麼都沒保護。多數人只驗第一道：「我寫了規則，它在檔案裡」。真正的失效住在 2 和 3。該問的從來不是「我加了規則沒？」，而是「它還在 fire 嗎？它的 output 是真的嗎？」

網路上的反應是在上面疊個 flashy 的東西：接 Obsidian「管理記憶」、讓一個 agent 監督另一個 agent，把整件事弄得看起來有被 organize。

memory vault 沒有逃離 dilution，它只是把 dilution 重新排列。那些筆記要起作用，還是得被讀回 window 裡，在那裡跟所有東西一樣搶注意力。儲存得漂亮一點，物理不變。

更隱微的版本：讓它記得更兇。更長的 config、更兇的提醒、更多 prompt。同一個問題，因為一條更大的規則，還是一條在跟下游所有東西搶注意力的規則。

判準不是文字存在哪裡，而是這機制要不要靠模型注意到它才生效。要，它就會被稀釋。唯一不會的，是那些完全在模型注意力之外運作的東西。

三、解法：把它搬出去

兩條路。一條是讓它記得更牢，註定失敗。另一條是承認它記不住，把重要的搬出去：搬到一個每個動作都會觸發的 script、一個權限切好的檔案系統、一份會自己編譯成規則的 log。搬到 window 碰不到的地方。

這就是核心動作。剩下的，都是同一個直覺在不同 scope 重複。

有一個分岔。你可以把東西搬成 primitives（檔案系統、一道閘門、一份 log），也可以搬成 scaffolding（為了補今天模型做不到的事而寫的指令）。模型越強，primitives 越有用，scaffolding 越是下一版要拆掉的東西。搬 primitives，模型變強時你不必為了它重做這層。

四、這些規則住哪

搬出去的東西要有地方住，而且不是同一個檔案。用一個問題分層：這條規則撐得過一場長對話嗎？ 撐不過，就沉下去。

層放什麼會衰減嗎
全域 config軟偏好：風格、語氣會，但無所謂
專案 config專案地圖：讀哪些檔、誰負責什麼會
Skills（命中才載入）主題規則，命中才載入不撐爆 context
Output style取代 system prompt、中段重注入抵抗，但非免疫
Hooks硬規則，每個動作觸發不會
Auto-memory跨 session 學習持久

準則：衰減了不會出事，就放上層；會出事，就沉下去。Hooks 是地基：它不住在對話裡，所以對話再長也稀釋不到。設計鐵則：deterministic 進 hook，discretionary 進 skill。任何「一定要發生」的事屬於 hook，絕不交給 skill 的 best-effort 比對。

五、我怎麼對抗它

每道防線對應 dilution 的一種失效方式。

硬規則沉進 hooks。一道寫入前的閘門（pretool_approval_gate.py）把檔案系統切成自由區（草稿、筆記、log）和正式區（README、上線網站、任何 user-facing 的）。一旦它伸手去碰正式區、或想寫超過一定行數，就被擋下，直到我最近的訊息裡帶了 approval token。這稀釋不掉，因為它不是 prompt 裡的一條規則，而是 prompt 外面的一道閘門，連在「跳過所有權限確認」的模式下都照樣觸發。「它現在被允許做什麼」這個判斷本身就是會在長 session 裡遺失的 state，所以我把那個判斷也搬出去了。

行為規則做成重注入的一層。output style 取代 system prompt 而不是附加，並隨對話變長重新注入，讓規則一直待在前面，不被擠到後面淡出。它還是住在 context 裡，所以它不免疫，只是住在 context 裡的東西當中最抗稀釋的那個。讓它和「記得更兇」分家的，是 replacement 和 recency：它把規則原地刷新，而不是在上面再疊更多文字。

糾正編譯成一份 log。每次我糾正它，一個 stop hook（stop_enforce_lessons.sh）就不准這輪結束，直到糾正落了地：做錯什麼、規則是什麼、根因是什麼。每條教訓帶一個 tag。[active] 代表我還在人工執行；一旦我把它移進某個 hook，就翻成 [codified]，它從此不再載入。這份 log 的重點不是存下糾正，是把糾正轉成機制：每條教訓最後都該變成一個 hook 或 skill，變了之後就不再載入 context，所以越用越輕。

Context 撐過 compaction。在對話被摘要掉之前，一個 hook（precompact_dump_plan.sh）把計畫 dump 到 disk，事後從 disk 重讀，不靠記憶。

這些沒有一個是關於模型的。全都是關於模型外面的結構。

六、Audit 它，否則它只是擺著好看

一個你不 audit 的機制，跟沒有機制無法區分。兩個我自己系統裡的真例。

我寫過一個 hook 強制自我批判（interrogate_enforce.py），卻從沒在任何 config 註冊。一整週，它觸發了零次，純粹的死碼，而我在心裡把它打勾當「做完了」。關卡 2 silent 失效。

同一週：上面那個管糾正 log 的 hook 去掃對話紀錄找「糾正信號」，但 tool output 被存成跟我打的字同一種 type，於是它一直比對自己讀進來的檔案，反過來指控我做了一堆沒發生的糾正。在跑、有 output、output 是垃圾。關卡 3 silent 失效。

驗一個機制有沒有接上線、活著，而不是它存不存在。「我加了規則」就是那個會害到你的答案。

七、你怎麼建自己的

由內而外，每一步都立刻有回報：

  1. 先建學習迴路。一份糾正 log，加一個「沒記下糾正就不准收尾」的 hook。先讓糾正會沉澱。
  2. 再建閘門。切自由區和正式區；便宜、可逆的全速跑，不可逆的停下來等你。這步讓你敢放手。
  3. 再做記憶工程。規則按衰減分層，該硬的沉進 hook。
  4. 持續 audit。驗每個機制有沒有在 fire，而不是存不存在。
  5. 保持精簡。定期問：這層是為今天的模型加的嗎？下一版會不會就變累贅？會，就拆掉。

所有雜訊底下的訊號就一句：模型是租來的，模型外面那層結構才是你自己的。別調那個正在被商品化的層，去建那個不會的。
