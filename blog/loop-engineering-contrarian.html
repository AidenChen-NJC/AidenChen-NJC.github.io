Loop Engineering

The new narrative on X: stop prompting line by line, go write the loop that prompts for you. But the logic is off — a loop is just while true. It's free, and it compounds single-step error exponentially. What's scarce isn't the loop; it's the constraint layer that keeps a runaway loop from costing you much.

The X hype: stop prompting, go write loops.
The logic is off. A loop is just while true. Free — and it amplifies your per-step error rate exponentially.
Autonomy isn't just automation; it's leverage — and it magnifies risk too.
What's actually scarce is the ability to call stop and correct.
The people getting this right aren't writing prettier loops. They're building a constraint surface where even if the loop goes wrong, it doesn't cost much.

1. What a loop is

Lately a narrative has been gaining traction on X: you shouldn't be prompting your coding agent line by line anymore — you should be designing the loop that prompts the agent for you. Addy Osmani named it “Loop Engineering.” Boris Cherny says he doesn't prompt Claude anymore either; he writes a loop, and the loop prompts Claude.

The hierarchy goes:

Prompt engineering   → the "words" you send
Context engineering  → "everything" the model can see
Harness engineering  → the "environment" the agent runs in (tools / sandbox / hooks / recovery)
Loop engineering     → the "iteration cycle" that drives the agent toward a goal

A loop is a recursive goal. Once the goal is set, the agent receives it on its own → thinks → acts → observes the result → repeats until a “verifiable stop condition” holds.

2. The logic underneath

Underneath, it's just ReAct (Reason + Act): think a step, do a step, look at the result, think again. Loop engineering just wires three add-ons onto that cell:

  • State: memory written outside the context (still usable across sessions).
  • Verifier: a second model that scores and validates the result.
  • Termination: step ceiling, token budget, stall detection, etc.

So the “loop engineering is a new paradigm” narrative really comes down to one sentence: the leverage shifts from “writing one good prompt” to “designing the control system that keeps prompting.”

The emotion it's actually selling is: what if we could pull the human — the bottleneck — out of the loop?

3. Where the value actually is

Suppose each AI step is 95% correct and you run 20 steps. End-to-end correctness drops to 36%:

0.9520 ≈ 0.36

This is compounding error. The model reads its own previous mistake back into context and is then more likely to carry it forward. Step 3 goes wrong, step 4 runs on polluted context, step 5 runs on “the pollution plus whatever step 4 added.”

Most people treat “autonomy” as the source of value. But autonomy by itself produces nothing.

while true is free. Anyone can write it in three lines. What's scarce was never the loop — it's a termination condition that's actually useful, and a verifier that actually sees the errors.

Flip it: a loop that calls a tested, reusable skill — that's what compounds. The value lives in the skill and the verifier, not in the loop.

4. How to use loops correctly

Most people write the loop first and think about verification later. I think it should be the other way around.

  1. Verifiability is the precondition, not a feature. If you can't write a checkable success condition, don't loop. Deterministic goals are easy (tests pass / CI green / lint clean). For fuzzy goals (“build this feature”), write the spec first and pin down what “done” looks like. This step is where loop engineering is genuinely hard — and genuinely valuable.
  2. Do it by hand first. You can't automate what you can't describe. Pick a boring process your team runs often, do it yourself three times, and write down the decisions you didn't realize you were making. That note is your skill.
  3. Get one agent, one flow, one measurable result working first. Don't start with five agents in parallel. Three 70% steps chained together is 34%. Prove that one is stable in your real environment before you scale out.
  4. Set up the verifier and termination. I keep an agent whose whole job is to attack the tools I build and surface my own vulnerabilities.
  5. A global-level lessons.md. Build a learning loop at both global and project level: write every debug session and every recurring Claude mistake into lessons.md, so each run keeps learning and applies what it learned before.
