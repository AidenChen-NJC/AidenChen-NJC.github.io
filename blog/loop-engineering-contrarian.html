Autonomy isn't just automation. It's leverage, so it magnifies risk too.
What's actually scarce is the ability to call stop and correct.
The people getting this right aren't writing prettier loops. They're building a constraint surface where a loop going wrong doesn't cost much.

1. What a loop is

Lately a narrative has been gaining traction on X: you shouldn't prompt your coding agent line by line anymore. You should design the loop that prompts the agent for you. Addy Osmani named it “Loop Engineering.” Boris Cherny says he doesn't prompt Claude anymore either; he writes a loop, and the loop prompts Claude.

The hierarchy goes:

Prompt engineering   → the "words" you send
Context engineering  → "everything" the model can see
Harness engineering  → the "environment" the agent runs in (tools / sandbox / hooks / recovery)
Loop engineering     → the "iteration cycle" that drives the agent toward a goal

A loop is a recursive goal. Once the goal is set, the agent takes it from there: think, act, observe the result, repeat, until a “verifiable stop condition” holds.

2. The logic underneath

Underneath, it's just ReAct (Reason + Act): think a step, do a step, look at the result, think again. Loop engineering wires three add-ons onto that cell:

  • State: memory written outside the context (still usable across sessions).
  • Verifier: a second model that scores and validates the result.
  • Termination: step ceiling, token budget, stall detection, etc.

So the “loop engineering is a new paradigm” narrative comes down to one sentence: the leverage shifts from writing one good prompt to designing the control system that keeps prompting.

The emotion it's actually selling: what if we could pull the human, the bottleneck, out of the loop?

3. Where the value actually is

Suppose each AI step is 95% correct and you run 20 steps. End-to-end correctness drops to 36%:

0.9520 ≈ 0.36

This is compounding error. The model reads its own previous mistake back into context and grows more likely to carry it forward. Step 3 goes wrong, step 4 runs on polluted context, step 5 runs on that pollution plus whatever step 4 added.

Most people treat “autonomy” as the source of value. But autonomy by itself produces nothing.

while true is free. Anyone can write it in three lines. What's scarce was never the loop. It's a termination condition that's actually useful, and a verifier that actually sees the errors.

Flip it: a loop that calls a tested, reusable skill is what compounds. The value lives in the skill and the verifier, not the loop.

4. How to use loops correctly

Most people write the loop first and think about verification later. I think it's the other way around.

  1. Verifiability is the precondition, not a feature. If you can't write a checkable success condition, don't loop. Deterministic goals are easy (tests pass / CI green / lint clean). For fuzzy goals (“build this feature”), write the spec first and pin down what “done” looks like. This is where loop engineering is genuinely hard, and genuinely valuable.
  2. Do it by hand first. You can't automate what you can't describe. Pick a boring process your team runs often, do it yourself three times, and write down the decisions you didn't realize you were making. That note is your skill.
  3. Get one agent, one flow, one measurable result working first. Don't start with five agents in parallel. Three 70% steps chained together is 34%. Prove that one is stable in your real environment before you scale out.
  4. Set up the verifier and termination. I keep an agent whose whole job is to attack the tools I build and surface my own vulnerabilities.
  5. A global-level lessons.md. Build a learning loop at both global and project level: write every debug session and every recurring Claude mistake into lessons.md, so each run keeps learning and applies what it learned before.

一、迴圈是什麼

最近 X 上有個敘事越來越紅：你不該再一行一行去 prompt 你的 coding agent，而該去設計那個替你 prompt agent 的迴圈。Addy Osmani 把它命名為「Loop Engineering（迴圈工程）」。Boris Cherny 說他也不再 prompt Claude 了；他寫一個迴圈，由迴圈去 prompt Claude。

這個層級是這樣的：

Prompt engineering   → 你送出的「文字」
Context engineering  → 模型能看到的「一切」
Harness engineering  → agent 運行的「環境」（工具 / 沙盒 / hooks / 復原）
Loop engineering     → 驅動 agent 朝目標前進的「迭代循環」

迴圈是一個遞迴的目標。目標一旦設定，agent 就接手：思考、行動、觀察結果、重複，直到某個「可驗證的停止條件」成立。

二、底層的邏輯

底層其實就是 ReAct（Reason + Act，推理＋行動）：想一步、做一步、看結果、再想。迴圈工程在這個基本單元上接了三個外掛：

  • 狀態（State）：寫在 context 之外的記憶（跨 session 仍可用）。
  • 驗證器（Verifier）：第二個模型，替結果打分與驗證。
  • 終止條件（Termination）：步數上限、token 預算、停滯偵測等等。

所以「迴圈工程是新典範」這套敘事，歸結成一句話：槓桿從「寫出一個好 prompt」轉移到「設計那個持續 prompt 的控制系統」。

它真正在販賣的情緒是：如果我們能把「人」這個瓶頸，從迴圈裡抽掉呢？

三、價值到底在哪

假設每個 AI 步驟有 95% 正確率，而你跑 20 步。端到端的正確率會掉到 36%：

0.9520 ≈ 0.36

這就是複利型的錯誤。模型把自己上一步的錯誤讀回 context，於是越來越可能把它延續下去。第 3 步錯了，第 4 步在被污染的 context 上跑，第 5 步又在那份污染、加上第 4 步新添的錯誤之上跑。

大多數人把「自主」當成價值的來源。但自主本身什麼都產不出來。

while true 是免費的，任何人三行就能寫出來。稀缺的從來不是迴圈，而是一個真的有用的終止條件，以及一個真的看得到錯誤的驗證器。

反過來看：一個會呼叫「經過測試、可重用的 skill」的迴圈，才會產生複利。價值住在 skill 和驗證器裡，不在迴圈裡。

四、怎麼正確地用迴圈

大多數人先寫迴圈，之後才想驗證的事。我認為順序剛好相反。

  1. 可驗證性是前提，不是功能。如果你寫不出一個可檢查的成功條件，就別用迴圈。確定性的目標很簡單（測試通過 / CI 綠燈 / lint 乾淨）。對模糊的目標（「把這個功能做出來」），先寫規格，把「完成」長什麼樣釘死。這正是迴圈工程真正困難、也真正有價值的地方。
  2. 先用手做一遍。你無法自動化你描述不出來的東西。挑一個你團隊常跑的無聊流程，自己手動做三次，把那些你沒意識到自己在做的決定寫下來。那份筆記就是你的 skill。
  3. 先讓一個 agent、一條流程、一個可量測的結果跑起來。別一開始就五個 agent 並行。三個 70% 的步驟串起來只剩 34%。在你真實的環境裡證明「一個」是穩的，再去擴張。
  4. 設好驗證器與終止條件。我會養一個 agent，它整份工作就是攻擊我做的工具、把我自己的漏洞翻出來。
  5. 一份全域層級的 lessons.md。在全域和專案兩個層級都建一個學習迴圈：把每一次 debug、每一個 Claude 反覆犯的錯都寫進 lessons.md，讓每一次執行都持續學習、並用上它之前學到的東西。
